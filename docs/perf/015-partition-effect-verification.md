# 015: 데이터 레이크 파티션 효과 검증 (Glue Crawler + Athena)

## 언제

- 날짜: 2026-08-12
- 관련 ADR: ADR 0012 (데이터 레이크 스키마/파티션 설계)
- 이 측정 직전에 무엇을 바꿨나: Glue Crawler로 S3 위 raw_events/
  fact_events 스키마 자동 인식, dt 파티션 등록.

## 실행 조건

- 스크립트: Athena 쿼리 콘솔에서 수동 실행
- 실행 환경: 실제 AWS 계정 (S3 + Glue + Athena)

## 결과 요약

| 쿼리 | Data scanned | 체감 |
|---|---|---|
| `SELECT count(*) FROM fact_events` (파티션 조건 없음) | 유의미한 차이 없음(데이터 규모가 작아 KB 수준) | 대기열/실행 시간 더 오래 걸림 |
| `SELECT count(*) FROM fact_events WHERE dt='...'` (파티션 조건 있음) | 유의미한 차이 없음(위와 동일 수준) | 대기열/실행 시간 더 짧음 |

## 관찰된 병목

지금 데이터 규모(하루치)에서는 스캔 바이트 수 차이가 거의 드러나지
않았다. 대신 실행 시간(특히 대기열 처리 시간) 차이가 먼저
감지됐는데, 이는 파티션 조건이 있으면 Athena가 "어느 파일을 열지"
판단하는 메타데이터 탐색 단계 자체가 빨라지기 때문으로 보인다.
파티션이 없으면 전체 파일 목록을 먼저 나열하는 과정부터 시작해
상대적으로 느리다.

데이터 양이 훨씬 커지면(수백만 건, 수년치로 누적) 스캔 바이트 수
차이도 커질 것으로 예상되나, 이번 검증에서는 데이터 규모의 한계로
그 효과까지는 실측하지 못했다. 파티셔닝의 이점이 "데이터 규모에
비례해서 커진다"는 걸 역으로 확인한 셈이다.
