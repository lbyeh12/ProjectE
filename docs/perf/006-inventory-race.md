# 006: 재고 동시성 검증

## 언제

- 날짜: 2026-08-09
- 관련 ADR: ADR 0004 (재고 동시성 제어 방식 선택)
- 이 측정 직전에 무엇을 바꿨나: 재고 컬럼 추가 + 비관적 락 기반 checkout()
  구현 (adrs/0004). 이 구현을 검증하기 위한 최초 측정.

## 실행 조건

- 스크립트: inventory_race_light.js (시나리오 1), inventory_race_crash.js (시나리오 2, 3)
- 목표 VU: 시나리오 1 - 10 / 시나리오 2 - 50 / 시나리오 3 - 10
- 지속 시간: 시나리오 1 - 즉시 종료(VU당 1회) / 시나리오 2, 3 - 30초
- 실행 환경: 로컬 Docker Compose, WORKERS=2 이상 (Spark는 시나리오 3에서만 실행)

## 관찰된 병목

**이중 쓰기 불일치가 실제로 재현됨.** checkout()이 Kafka 전송을
db.commit() 이전에 하는 구조라, 재고를 확보한 요청이 Kafka 전송 후
커밋 전에 죽으면 DB 트랜잭션은 롤백되지만 Kafka 메시지는 이미 나가
있어 되돌릴 수 없다. 그 재고를 다른 요청이 다시 확보해 정상 커밋되며,
최종적으로 Kafka 쪽 이벤트 수가 DB보다 1건 많은 상태로 남았다.

부수적으로 응답 유실 케이스도 관찰됨: k6 기준 purchase_success는
4건인데 DB 기준 재고 감소분은 5건 — 커밋까지는 성공했으나 200 응답이
클라이언트에 전달되기 전에 연결이 끊긴 요청이 있었던 것으로 보인다.
사용자 입장에서는 실패로 인식해 재시도할 상황이라, 멱등성 처리가
없는 현재 구조에서는 중복 처리로 이어질 수 있다.

이건 애플리케이션 로직(Kafka 전송/commit 순서, 멱등성 부재)의 문제이지,
테스트 환경의 리소스 한계는 아니다. 다만 개발 모드(--reload)에서는
이 시나리오 자체가 재현이 안 됨을 별도로 확인했다: --reload는
"리로더(PID 1) + 자식 서버" 구조라 자식이 os._exit()로 죽으면 복구가
안 되고 컨테이너는 Up 상태인데 응답 불가로 멈춘다. WORKERS>=2
(--workers 모드)로 띄워야 마스터가 죽은 워커를 즉시 재기동해서
정상적인 장애 복구 시나리오가 된다.
