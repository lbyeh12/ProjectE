# ADR 0004: 재고 동시성 제어 방식 선택

## Status

Accepted

## Context

지금까지의 부하 테스트는 "일반적인 트래픽 혼합"(상품 조회 다수 +
구매 소수)을 대상으로 했다. 001-baseline.md에서 발견한 문제(계정
동시 사용으로 인한 장바구니 레이스 컨디션)를 계기로, 실제 이커머스
서비스에서 흔히 생기는 "한정된 자원을 여러 사용자가 동시에 노리는"
상황(재고 경쟁)을 의도적으로 재현하는 시나리오가 필요해졌다.

이 시나리오를 실제와 비슷하게 만들려면 두 가지가 선행되어야 했다.
데이터셋의 가격이 원본 GBP라 실무환경인 원화로 변환했고(1000원 단위 반올림), 
상품에 재고 수량이라는 개념 자체가 없어서 이를 추가한다.

재고는 "결제 흐름의 정합성"과 직결되는 문제이다.

## Decision Drivers

- 재고가 실제로 있는 수량보다 더 많이 팔리는 일이 없어야 한다
  (초과 판매 방지).
- 처리 중 서버가 죽거나 연결이 끊기는 비정상 상황에서도 재고
  데이터가 깨지지 않아야 한다.
- 재고/결제 흐름이라, 구현이 복잡해서 생기는 버그 위험보다 로직의
  단순함과 확실함을 우선한다.

## Considered Options

1. **비관적 락 (SELECT ... FOR UPDATE)**
   - 재고를 조회하는 순간 해당 행을 잠궈서, 다른 트랜잭션이 같은
     행을 건드리지 못하고 대기하게 만든다.
   - 결제 완료(커밋)까지 락을 유지하면, "먼저 온 요청이 처리되는
     동안 나머지는 확실히 기다린다"는 게 보장된다.
   - 대기가 몰리면 처리량이 떨어질 수 있다는 단점이 있다.
2. **낙관적 락 (버전 컬럼 + 재시도)**
   - 락 없이 다들 동시에 조회하게 하고, 실제 업데이트 시점에
     "내가 본 버전과 지금 버전이 같은지" 확인해서 다르면 실패시킨다.
   - 충돌이 나면 애플리케이션이 재시도 로직을 따로 구현해야 하고,
     재시도 중 다시 실패할 경우 사용자에게 실패로 보일 수 있다.
   - 결제처럼 "확실한 처리"가 중요한 흐름에는 재시도 로직의 복잡도가
     오히려 부담이 된다고 판단했다.
3. **메시지 큐 기반 순차 처리**
   - 재고 차감 요청을 큐에 넣고 하나의 워커가 순서대로만 처리하게
     만들어 동시성 문제 자체를 없앤다.
   - 가장 확실하지만, 지금 규모에 비해 구현/운영 복잡도가 크게
     늘어난다고 판단했다.

## Decision

**비관적 락을 채택한다.** 재고/결제는 누락되는 요청이 없어야 하고
중간에 끊기더라도 안전하게 복구 가능해야 하는 흐름이라, 대기가 생겨도
"먼저 온 순서대로 확실히 처리"가 보장되는 방식이 낙관적 락의 재시도
방식보다 이 문제에 더 직접적으로 맞는다고 판단했다.

락은 재고 조회 시점부터 결제 완료(커밋)까지 유지한다. 재고 차감과
주문 생성은 하나의 트랜잭션으로 묶어서, 커밋 전에 서버가 죽으면
전체가 자동으로 롤백되게 한다.

## Consequences

- **좋아지는 점**: 재고가 실제 수량보다 더 많이 팔리는 일이 구조적으로
  방지된다. 처리 중간에 서버가 죽어도 트랜잭션 단위로 롤백되어 재고
  데이터가 항상 일관된 상태를 유지한다.
- **감수해야 하는 점**: 같은 상품에 대한 요청이 몰리면, 락을 기다리는
  대기 시간이 늘어나 응답이 느려질 수 있다. 이게 실제로 얼마나
  영향을 주는지는 재고 경쟁 시나리오로 부하 테스트를 할 예정이다.
