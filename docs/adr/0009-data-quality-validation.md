# ADR 0009: 데이터 품질 검증 도구로 Great Expectations 도입

## Status

Accepted

## Context

지금은 이벤트가 들어오는 대로 `raw_events`에 그대로 저장된다.
음수 가격, 미래 timestamp, 존재하지 않는 `user_id`/`product_id`를
참조하는 이벤트가 섞여도 걸러내지 못한다. ADR 0008에서 도입하는
차원 모델(`fact_events`)이 이런 불량 데이터를 그대로 반영하면
분석 결과 자체가 왜곡된다.

## Decision Drivers

- 검증 실패한 데이터는 파이프라인을 막지 않고, 별도로 격리해서
  원인을 나중에 조사할 수 있어야 함.
- 검증 규칙을 코드로 버전 관리하고, 어떤 규칙이 왜 있는지 문서화
  되어야 함.
- 기존 배치(Airflow) 흐름에 자연스럽게 끼워 넣을 수 있어야 함.

## Considered Options

1. **Great Expectations** — 데이터 검증 전용 오픈소스, "expectation"
   단위로 규칙을 선언적으로 작성. 검증 결과를 리포트(HTML/JSON)로
   남겨 실패 원인 추적이 쉬움. 데이터 엔지니어링 직무에서 표준
   도구로 자주 언급됨.
2. **Pandas/SQL로 직접 검증 스크립트 작성** — 별도 의존성 없이
   바로 시작 가능. 다만 규칙이 늘어날수록 코드가 파편화되고,
   검증 결과 리포트를 직접 만들어야 함.
3. **Pydantic 스키마 검증만 강화** — FastAPI 진입 시점 검증은
   이미 일부 존재(이벤트 스키마). 다만 이건 "형식이 맞는가"만
   보고 "값이 의미상 타당한가"(가격 음수, 참조 무결성)는 못 거름.

## Decision

**Great Expectations를 채택한다.** 검증 규칙을 선언적으로 코드에
남길 수 있어 유지보수가 쉽고, 실패 리포트가 표준화되어 있어 원인
조사 부담이 적다. Airflow `daily_etl` DAG의 변환 단계 앞에
검증 태스크를 추가하는 방식으로 기존 흐름에 끼워 넣는다.

검증 규칙 예:

```
- price >= 0
- timestamp <= 현재 시각
- user_id가 존재하면 users 테이블에 있는 값이어야 함 (참조 무결성)
- product_id가 존재하면 products 테이블에 있는 값이어야 함
- (user_id, product_id, event_type, timestamp) 완전 중복 제거
```

검증 실패 건은 `quarantine_events` 테이블에 원본 데이터 + 실패
사유와 함께 격리한다. 파이프라인은 실패 건이 있어도 중단되지 않고
나머지 정상 건으로 계속 진행한다.

## Consequences

- **좋아지는 점**: 차원 모델(ADR 0008)에 불량 데이터가 반영되는
  것을 막는다. 격리된 데이터와 사유가 남아 원인 조사가 쉬워진다.
- **감수해야 하는 점**: 검증 단계가 배치 실행 시간을 늘린다.
  격리 테이블이 계속 쌓이므로 주기적 정리가 필요하다.
- **후속 작업**: 격리 건이 특정 유형에 몰리면(예: 특정 컴포넌트의
  버그로 반복 발생), 근본 원인을 소스 쪽에서 수정.
